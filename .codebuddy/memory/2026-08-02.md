## 新分析文档：DP Prefill-Balancing 深度剖析
- 用户问：vLLM 为什么好端端的有个 DP prefill-balancing 操作？
- 产出：`.codebuddy/analysis/dp_prefill_balancing.md`（新建，源码未改动）。
- **核心结论**：
  - 问题根源：DP 多副本部署下各 rank 独立决定 prefill 时机 → 因请求长度方差 + prefill/decode 计算量悬殊，出现"快 rank 在 decode、慢 rank 在 prefill"的错步 → DP 同步点（wave all-reduce / EP all-to-all）处快 rank 干等慢 rank，GPU 利用率暴跌（木桶效应）。
  - 解法：cadence 对齐。配置 `prefill_schedule_interval`（config/scheduler.py:153，默认 1=关闭）。`DPEngineCoreProc._should_throttle_prefills`（engine/core.py:1916）用 `step_counter % interval != 0` 判定非对齐步，无需通信（step_counter 由 wave 边界 all-reduce 同步、每步+1，是跨 rank 逻辑时钟）。
  - 调度器 `defer_prefills`（scheduler.py:459）三条件：throttle_prefills AND not prefill_capacity_bound AND running 中有纯 decode 请求。作用点 A：running 中 is_prefill_chunk 本步跳过（留队不抢占，scheduler.py:494）；作用点 B：waiting 首个待压抑 prefill 即 break（:848）。
  - **安全阀** `prefill_capacity_bound`（scheduler.py:293/1082）：cadence 步末若 waiting 未清空 → 置 True → 后续错开步也放行，防 TTFT 雪崩；某 cadence 步清空 waiting 后自动关。
  - 与 MoE/EP 强相关：`DPEngineCoreProc` 断言 `is_moe`（core.py:1759）——价值在 MoE 的 EP all-to-all 要求各 rank token 数尽量对齐。
  - wave 边界 step_counter 归零（core.py:1981）→ 新 wave 首步必为 cadence 对齐步，立即接纳 prefill。
- 关键源码行号：config/scheduler.py:153；engine/arg_utils.py:611/1458/2167；engine/core.py:474(基类恒False)/1916(DP版)/1981(归零)/1987(+1)/1759(is_moe断言)；core/sched/scheduler.py:287-293(安全阀定义)/444-461(defer判定+注释)/494(作用点A)/848(作用点B)/1076-1082(安全阀更新)；interface.py:72(形参文档)；tests/v1/core/test_scheduler.py:378/383。

## 新分析文档：Speculative Decoding 深度解剖
- 用户用 source-analyzer skill 要求"调研+源码分析+报告"投机解码完整链路（调度/执行/验证/闭环）。
- 产出：`.codebuddy/analysis/spec_decode.md`（新建，源码未改动）。含 Mermaid 架构图/状态图/端到端时序图、FAQ 逐条解答用户原始疑问。
- **核心结论（一句话链路）**：
  - 调度：`allocate_slots(num_lookahead_tokens=K)` 多预留 K 个 KV slot（scheduler.py:569-573，num_lookahead_tokens 在 :245-257 按 method 设定）；读 `request.spec_token_ids`（上轮草稿）→ 复制进 `scheduled_spec_decode_tokens` → **立即清空** `req.spec_token_ids=[]`（:632-647）。
  - 执行：`_calc_spec_decode_metadata`（gpu_model_runner.py:2798）拼 `[真实 + draft×K + bonus]`，target 一次前向把 KV 写入（含草稿位置 slot）；`RejectionSampler.forward`（rejection_sampler.py:88）用 bonus + 草稿位置拒绝采样保证无损；`propose_draft_token_ids`（:4913）调 `self.drafter.propose` 生成下一轮草稿。
  - 闭环：`update_from_output`（:1654-1685）统计 accepted/rejected、回退 `num_computed_tokens`；`update_draft_token_ids`（:2020-2040）把新草稿写回 `req.spec_token_ids` → 下一轮复用。
- **关键纠正**：`spec_token_ids` 不是"上轮记录的历史 input"，而是验证后由 drafter 新生成的"待验证草稿"暂存桶，调度器只中转不累积；真正 input 拼接在执行层。
- 方法族：EagleProposer / DraftModelProposer / NgramProposer(GPU) / MedusaProposer / SuffixDecodingProposer / Gemma4/Step3p5/DFlash MTP 等，入口 `vllm/v1/spec_decode/`，统一 `propose()` 接口。

## 抢占与 in-flight output 竞态（test_preempt_during_execution 解读）
- 用户追问 `tests/v1/core/test_scheduler.py:1008-1021`：请求被抢占后，才用抢占前那步的 `scheduler_output1` 调 `update_from_output`，是否有问题。
- 结论：**没问题，该测试正是为锁定这一竞态而写**（`max_concurrent_batches>1`/PP/异步调度下是常态，注释见 `:982-983`）。
- **核心原则：抢占只回收 KV 与计算进度，绝不丢 token。** `_preempt_request`（scheduler.py:1211-1233）只做 `_free_request_blocks` + `status=PREEMPTED` + `num_computed_tokens=0` + `spec_token_ids=[]` + `waiting.prepend_request`，**不动 `_output_token_ids`**。
- `update_from_output` 三处容错保证迟到 output 能安全落到已抢占请求：
  1. `:1638-1647` 存活性检查用 `self.requests.get()` + `is_finished()`——PREEMPTED 请求仍在字典中且未 finished，正常处理不被 skip。
  2. `:1673` `if request.num_computed_tokens > 0` 下界保护——抢占已清零，挡住负数下溢。
  3. `:1785-1788` + `:1834-1836` 用 `status_before_stop` 分流：停止前 RUNNING → 从 `self.running` 移除；停止前 PREEMPTED → 从 `self.waiting` 移除（注释自称 "rare case"，正是此竞态）。
- 后果：requests[1] 变为 PREEMPTED / num_computed_tokens=0 / output_token_ids=[42] / 躺 waiting 队首；重调度时从头 prefill 81 token（80 prompt + 已输出的 42）。代价是重算，正确性无损。

- **事实**：`generated_token_ids`（= `sampled_token_ids[req_index]`）在投机解码下的顺序是 **accepted（对上一轮草稿的验证结果）在前，sampled/bonus（本轮真采样新 token）在最后 1 位**。

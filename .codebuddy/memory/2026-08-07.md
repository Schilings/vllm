## DeepSeek-V4 文档第十轮纠错：C4-state group 含 22 层 KV cache（用户强调）
用户指出：c4state group ③ 还包含 11 层的 indexer compressor states，共 22 层 KV cache，不能漏。
- 核实：`group_and_unify` 按 `(block_size, sliding_window)` 分桶，③=(4,8) 含**主C4 compressor state(11层,37440) + indexer内C4 compressor state(11层,8640)** → spec 总 22 层，但按 page 分两桶、每桶 11 层。

- 修正：§5.1.4.2/3/4 明确组③=22 层（11主+11indexer内），§5.2.2 推演强调"c4state 共 22 层 KV cache"。

- ⚠️ `get_num_layer_tuples` vs 总层数 的区别是易错点：它数的是"most_common page 的 tuple 数"，多 page 桶的 spec 总层数会大于它。

## DeepSeek-V4 文档第十一轮纠错：total_num_bytes_per_block 按 slot 算，非按段算（用户指出）
用户指出：文档里 `total_num_bytes_per_block` 算错了——不是所有段的求和，而是**所有 slot 的求和**，同一 slot 跨 group 复用，只算一次！

核实源码 `kv_cache_utils.py:1414`：
```python
total_num_bytes_per_block = sum(ps * len(slots) for ps, slots in buckets.items())
```
`len(slots)` 是**该 page_size 的 slot 个数**，每个 slot 只数一次。同一 slot 被多个 group 回填（full_mla 建的 37440 slot 被 SWA/c4state/c128state 复用），物理只占一份字节。把各 group 段数全加起来（54+22+10）再乘 page_size 是**重复计算**。

修正：
- §5.2.3 总字节改为 **slot 求和**：`37440×11 + 8640×11 + 1728×10 = 524,160 字节/block`（旧错 2,229,120）。无 indexer = `37440×11 + 1728×10 = 429,120`（旧错 2,039,040）。
- §5.2.2 上方坑注释、buckets 图注、§5.2.3 结构图注、§5.4 显存公式同步修正为 slot 视角；段数 54/22/10 改标注为"slot 内部内容计数，不拿去乘 page_size"。
- 新增醒目警示框：源码 1414 行按 slot 算。

⚠️ **第九轮记忆作废修正**：第九轮结论"总字节必须按段数算"是**错的**，已在本轮改为按 slot。段数（54/22/10）只是 slot 内回填的层数计数，决定 slot 内部布局，但不影响 `total_num_bytes_per_block`（它只数 slot 个数×page_size）。
